# Дедупликация assets в собранном Hugo-сайте

## Цель

Сократить дисковое пространство, занимаемое медиафайлами, которые хранятся как исходные assets в каталоге бэкапа и повторно копируются Hugo в `site/public`.

Готовый сайт должен сохранить текущую структуру URL и работать с существующей конфигурацией nginx. Оптимизация ориентирована на локальную раздачу сайта, когда каталог бэкапа и `site/public` находятся на одной файловой системе.

## Выбранный подход

После обычной Hugo-сборки копии assets в `site/public` заменяются hardlink-ссылками на соответствующие исходные файлы из каталога бэкапа.

Hardlinks предпочтительнее символических ссылок, потому что nginx и другие программы видят их как обычные файлы. Они не зависят от относительного расположения каталогов и не позволяют получить битую ссылку при изменении имени родительского каталога.

## Поток сборки

1. Перед запуском Hugo существующий `site/public` полностью удаляется как generated artifact.
2. Hugo создаёт новый самодостаточный `site/public` обычным способом.
3. Post-processing проходит по исходным файлам `assets/` в каталоге бэкапа.
4. Для каждого исходного файла ищется соответствующий файл по тому же относительному пути внутри `site/public`.
5. Перед заменой проверяется, что оба файла имеют одинаковый размер и содержимое.
6. Public-копия атомарно заменяется hardlink-ссылкой на исходный файл.
7. Скрипт выводит количество созданных hardlinks, количество пропущенных файлов и оценку сэкономленного места.

Полное удаление `site/public` перед каждой сборкой обязательно. Оно гарантирует, что Hugo не откроет существующий hardlink на запись и не повредит тем самым исходный asset.

## Сопоставление путей

Исходный файл:

```text
<output_dir>/<platform>/<author>/posts/<slug>/assets/<file>
```

Соответствующий файл сайта:

```text
site/public/<platform>/<author>/posts/<slug>/assets/<file>
```

Алгоритм использует путь относительно `output_dir`, поэтому поддерживает все платформы и авторов без отдельных правил.

## Обработка ошибок

- Если public-файл отсутствует, исходный файл пропускается.
- Если размер или содержимое различаются, public-файл сохраняется как обычная копия.
- Если hardlink невозможно создать из-за разных файловых систем (`EXDEV`), public-файл сохраняется как обычная копия.
- Ошибка обработки одного файла не должна удалять рабочую public-копию.
- Замена выполняется через временный hardlink в каталоге назначения и атомарный `rename`.
- Ошибка самой Hugo-сборки остаётся фатальной; post-processing после неё не запускается.

Таким образом, невозможность оптимизации не делает сайт неработоспособным и не влияет на исходный бэкап.

## Локальная и Docker-сборка

Локальный `site/build.sh` очищает `site/public`, запускает Hugo и затем выполняет дедупликацию.

При Docker-запуске Hugo продолжает собирать сайт в контейнере. Дедупликация запускается на хосте из `run-docker.sh` после успешного завершения Hugo, поскольку отдельные bind mounts могут запрещать создание hardlinks между каталогами даже тогда, когда хостовые пути находятся на одном диске.

Команда сервиса Hugo также очищает `public` перед сборкой. Поэтому прямой вызов `docker compose run --rm hugo` безопасно создаёт корректный, но недедуплицированный сайт. Рекомендуемый `run-docker.sh` дополнительно выполняет дедупликацию на хосте при наличии поддержки hardlinks.

## Компоненты

- Отдельный Bash-скрипт `site/deduplicate-assets.sh` принимает `output_dir` и `site/public` как явные аргументы. Он использует доступные в Linux базовые утилиты и не добавляет Python-зависимость на Docker-хосте.
- `site/build.sh` вызывает скрипт после Hugo-сборки.
- `run-docker.sh` вызывает его на хосте после Docker-сборки Hugo.
- Команды Hugo в обоих compose-файлах очищают `public` перед сборкой, даже если дедупликация не запускается.
- Код скачивания и формат Markdown не меняются.
- Hugo-шаблоны и URL assets не меняются.

## Безопасность данных

Каталог бэкапа является каноническим источником и никогда не изменяется скриптом дедупликации. Скрипт удаляет или заменяет только файлы внутри generated-каталога `site/public`.

Проверка границ путей обязательна: оба аргумента нормализуются, а заменяемый файл должен находиться внутри `site/public`. Символические ссылки внутри обхода не используются как исходные файлы.

## Тестирование

Автоматические тесты должны проверять:

- замену идентичных файлов hardlink-ссылкой с одинаковым inode;
- сохранение public-копии при различающемся содержимом;
- безопасный fallback при `EXDEV`;
- отсутствие изменений исходного файла;
- отказ от обработки пути за пределами `site/public`;
- корректную статистику обработанных и сэкономленных файлов;
- отсутствие post-processing после неуспешной Hugo-сборки;
- полную очистку старого `site/public` перед повторной сборкой.

Интеграционная проверка должна выполнить две последовательные сборки и подтвердить, что исходные assets не изменились, а итоговый сайт продолжает открывать медиафайлы.

## Вне области изменений

- Дедупликация одинаковых assets между разными постами.
- Изменение структуры бэкапа или URL медиафайлов.
- Настройка nginx `alias` для отдельного media-каталога.
- Гарантия экономии места на разных файловых системах.
- Создание переносимого `site/public` с сохранением hardlink-связей после копирования на другой диск.
